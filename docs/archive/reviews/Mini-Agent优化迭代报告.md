# Mini Agent 优化迭代报告（复核版）


当前最该解决的是三件事：
让一次评测的配置和成本可复现、让真实工具具备最小权限与停止边界、让运行数据可控地留存与清理。跨会话记忆、远程 MCP、多 Agent 等能力有价值

本次按当前代码复核，重点检查了 `backend/app/services/evaluations.py`、`agent_runtime.py`、`runs.py`、`models.py` 及对应前端页面。评测与运行记录的后端定向测试 10 项通过；前端 101 项测试与生产构建通过。构建同时提示主 JavaScript 文件压缩后为 506 KiB，属于后续性能项。

本文是代码审查结论，不替代真实模型、MCP 服务和浏览器端到端验收。

## P0：先修复正确性问题

### 1. 评测必须真正使用创建时快照

`EvaluationTask` 创建时保存了 Agent 快照，但 `_run_case` 会重新读取 Agent、模型、提示词和能力绑定。评测期间修改 Agent，后续用例可能换了配置，任务详情却仍像是在比较同一版本。

实现方式：把任务快照扩展为执行快照，包含模型标识、温度、输出上限、提示词版本与正文、工具/Skill/MCP 的稳定标识和内容版本。Runtime 接受受限的快照输入执行；能力被停用或解除绑定时仍立即拒绝执行。外部 MCP 无法冻结时，记录配置指纹并在变化时中止任务。

验收：运行中修改提示词或模型参数，任务要么继续使用原快照，要么中止并要求新建任务；不得静默混用。

### 2. 评分重试必须累计全部 Token

评分器允许第二次修正 JSON 格式，但当前 `usage` 被第二次请求覆盖，保存的 Token 不含第一次失败尝试。

实现方式：每次尝试分别保存 usage，再汇总输入、输出、缓存输入与总 Token；任一次未返回 usage 时将总口径标为“不完整”。

验收：模拟“第一次格式错误、第二次成功”，累计数值覆盖两次请求，耗时和尝试次数一致。

## P1：下一阶段应交付的闭环

### 3. 可计价、可复现的运行成本

模型已有三类价格字段，Run 已记录部分 Token，但价格没有币种、计价单位和历史快照。数字 `1` 代表每千 Token、每百万 Token还是其他单位无法判断，历史成本也会随模型配置修改而变化。

先在模型配置中明确 `currency` 与 `price_per_tokens` 的单位，再在 Run 中保存价格快照和成本完整性。计费应为：非缓存输入、缓存输入、输出三项分别计算；缺 usage 或价格时显示“未知/不完整”，不能显示 0。

评分与上下文压缩也应独立记账，避免把它们误认为业务回复成本。

### 4. 评测可取消、可恢复、可解释

服务重启会安全地把运行中的评测标记为中断，这部分已存在；但 API 和界面没有“停止评测”入口，用户启动较长数据集后无法主动取消。

增加停止接口和按钮，调用已有 `Cancellation`，将未处理用例保留为待处理、执行中/评分中的用例标记中断原因。任务详情还应展示被测 Run、评分尝试、评分模型快照和失败类别，便于区分“Agent 答错”“运行失败”“评分失败”。

### 5. MCP 最小权限与执行预算

本地工具已有启停、参数校验、文件边界和 Shell 沙箱；问题在于 MCP 目前按整个 Server 绑定，Agent 不能精确到单个 MCP 工具授权。并且最大模型轮数不能限制每轮多个工具调用，也不能限制总耗时或总成本。

先做四个固定边界：

- Agent 绑定 MCP 时选择具体工具，默认不新增授权。
- 运行限制总时长、工具调用次数、Token/费用预算；未知费用时仍按时长与次数生效。
- 同一工具、同一参数连续失败达到阈值后熔断，并给出原因。
- 对写入或外部副作用工具增加人工定义的风险级别；需要确认的操作必须在本次运行中明确授权。

幂等键应由每个外部业务工具的 API 协议定义，不能由 Runtime 假设实现。

### 6. 运行数据生命周期

Run 会长期保留工具输入与结果载荷，评测也会保留问题、回答和评分理由。目前没有运行记录或评测任务的删除、保留期限和容量策略。即使已有字段名脱敏，业务文本仍可能包含敏感内容。

增加本地数据管理：按 Run、会话和评测任务删除；设置默认保留期限或最大容量；删除时级联清理事件和详细载荷。调试载荷默认最小化保存，完整载荷必须明确启用并标注风险。

### 7. MCP JSON 导入与安全导出

在现有表单旁增加 JSON 粘贴导入，支持常见 `mcpServers` 的 stdio 结构。导入前预览名称、命令、参数和环境变量名；拒绝 URL 型远程配置并说明当前只支持本机 stdio。导出默认不包含环境变量值。

导入只保存草稿或配置，不能自动测试、启动或执行命令。

## P2：在 P0/P1 稳定后迭代

### 8. 把运行记录变成可比较的观察面板

现有页面已能按状态和 Agent 查看 Run，并能下钻时间线。下一步是补时间范围、来源（聊天/评测）和模型筛选，以及统一口径的成功率、P95 耗时、首字延迟、Token、工具错误率和成本。每个指标都应能跳转到对应明细。

先定义口径：取消是否进入成功率分母、部分完成如何统计、usage 不完整是否计入成本。没有口径的仪表盘只会制造误判。

### 9. 评测从“LLM 打分”升级为“可定位的问题集”

保留 LLM 评分，同时增加确定性规则和过程指标。用例逐步支持历史消息、前置条件、期望工具和结构化断言；失败结果能标注类别、人工复核和处理状态；只重跑失败项时保留原始结果。

只有数据集版本、执行快照和评分口径一致的任务，才允许做通过率、成本和耗时对比或发布门禁。

### 10. 上下文压缩的质量与诊断

压缩已具备阈值、回退、取消保护和事件记录，不需要重写。增加针对用户目标、已确认事实、限制条件、工具结论和未完成事项的回归用例；运行详情展示触发原因、压缩前后估算 Token、实际压缩轮次和回退原因。

Token 估算与供应商实际 usage 必须分开展示。

### 11. 受控诊断与前端性能

诊断页默认展示配置版本、能力清单、模型请求哈希、估算 Token 和脱敏事件摘要。查看原始载荷应是单次、受权限和保留期限控制的操作，不能把完整提示词设为默认日志。

前端构建的主包已超过 500 KiB 警戒线。观察页、评测页和代码高亮适合按路由懒加载；拆分后以真实首屏加载和交互性能复测，不为消除警告盲目切包。

### 12. 跨会话记忆的最小闭环

仅在课程作业或明确需要复用偏好时实现。第一版只保存用户明确确认的记忆，提供来源、查看、编辑和删除；新会话按相关性和上下文预算注入。自动提取、向量检索和“永久记忆”后置。

验收：会话 A 保存、会话 B 命中；更正后旧事实失效；删除后不再召回；未命中不编造。若未来支持多用户或多个工作空间，记忆必须先完成隔离。

## 明确不进入当前迭代

远程 MCP、定时回归、多 Agent 编排、Skill 脚本执行、Skill 附件自动读取、面向普通用户的配置隐藏和暗色模式都不应抢占当前工作。它们需要独立场景、权限模型和验收标准。

## 推荐顺序

1. 修复评测快照与评分重试统计，补对应回归测试。
2. 定义价格单位与币种，完成运行、评分、压缩的价格快照和成本计算。
3. 增加停止评测、MCP 单工具白名单、总预算与运行数据清理。
4. 完成 MCP JSON 导入，降低配置成本。
5. 用固定用例补过程评分、版本对比、压缩和记忆验证，再建设聚合观察面板。
6. 有真实需求后再做跨会话记忆与 P3 产品扩展。

衡量本轮是否完成的标准很简单：同一份评测可以复现；一次运行能知道用了什么、花了多少、为什么停下；用户能及时取消、限制和删除本地数据。
